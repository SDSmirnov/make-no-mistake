# T2 reference

Read this before any T2 work. It extends [`SKILL.md`](../SKILL.md); read [`references/verifier.md`](verifier.md) and [`references/evidence.md`](evidence.md) alongside it.

## Mandatory fresh-context verifier

For T2, a fresh-context verifier (isolated subagent, separate clean CLI process, or human per [`references/verifier.md`](verifier.md)) is mandatory, even for purely local pre-gate work. Do not substitute solo review.

- **When direct checks exist here** (executed or primary-source), the verifier must have tool access to run independent falsification or primary-source checks. Re-running a mock test unexamined does not count. It must either surface an evidenced defect or report the concrete checks (with provenance) and artifact traces that held.
- **When all direct behavioral checks are blocked** (for example, a static migration-plan sign-off with no disposable database), it must trace failure paths against the primary artifact, tag them `inferred`, and name the blocked checks.
- **When fresh context or required check access is unavailable** (neither isolated subagents nor a separate clean CLI model invocation can run), stop and report the gap unless a recorded verifier waiver covers it. Approving an execution gate does **not** silently waive a missing verifier. Never describe an unexecuted check as performed.

Pass the verifier only the redacted request, contract, artifact or diff, primary sources or datasets, logs, and local/ephemeral check commands. Never pass live credentials or authorization to cross the gate boundary.

## Risk ledger and compaction persistence

Track every material T2 risk in a ledger with provenance, or the named blocker when a check cannot run safely here:

| # | Risk | Severity | Check | Evidence (command/source, oracle, provenance) | Status |
| - | ---- | -------- | ----- | --------------------------------------------- | ------ |
| 1 | Trusted proxy collapses distinct clients into one bucket | high | Two requests via trusted proxy with distinct client IPs increment separate keys | `pytest tests/test_rate_limit.py::test_trusted_proxy_distinct_clients -q` → 1 passed; oracle: `docs/auth-policy.md:14-29`; `feat/login-rate-limit` @ `abc1234`, repo root, local, exit 0 | passed |

`"Checked"` without a command or authoritative source, oracle, and provenance is not evidence. An empty or blocker-marked cell shows what you have not earned.

**Persist across context compaction.** In T2 or long multi-step sessions, keep the redacted contract and risk ledger in a private (`0600`), untracked scratch file outside git commits:

- Use an ignored `.mnm-ledger.<session>.tmp` in the worktree (when workspace-sandboxed) or a `mktemp` file under `$XDG_RUNTIME_DIR` (`umask 077`, never world-readable shared `/tmp` with a predictable name).
- Never commit it unasked, and delete it when done unless the user asks to keep it.
- Update it as checks complete, and re-read it after context compaction and before verifier passes, gate packets, and final reports so open `high` risks and blockers cannot drift.

## Waivers and risk acceptance

You cannot self-waive or silently downgrade T2. An upfront "skip checks/gates" request made before the risk is visible is never an informed waiver.

A waiver changes the accepted risk, not the evidence status. It never upgrades an unverified claim to verified. Nor does it turn `inferred` into `passed` or `verified`.

**Verifier or check-access waiver:**

- Allowed **only when a fresh-context verifier or required check access is unavailable** in the harness or environment, after you state the concrete gap and risk.
- Record who waived what, for which scope (plus window/expiry if standing), and the accepted risk; keep solo evidence bounds (`executed checks verified, unexecuted behavioral claims inferred`).
- For purely local pre-gate work in their own worktree, the interactive user can accept the risk of a missing verifier or check access.
- For live, shared, third-party, personal-data, or organizational scope, a waiver requires a decision owner acting within their authority.
- No waiver overrides restrictions on other people's data, credentials, or shared/organizational environments.

**Execution gate:**

- Never skip presenting the gate packet before crossing the gate boundary.
- An authorized human may approve the packet while explicitly accepting a named residual risk, such as an untested rollback or a blocked pre-check. Record it in `Approval` with scope and window/expiry.

## The gate packet

Before crossing the gate boundary, stop and present the pre-gate report (with ledger) together with this decision packet. Keep it redacted and short enough to decide from. Skip the packet for pre-gate local work. Sign-off-only reviews audit against these same fields and deliver the sign-off report below as the gate input.

```text
Action: <exact command/change, target environment, account, version/commit>
Blast radius: <who and what are affected; worst realistic outcome; reversibility (technical, data, information, operational)>
Pre-state: <baseline, health/metrics; backup/snapshot id and restore test, or "n/a — no data mutated">
Rollback/compensation: <steps, duration, state cleanup, tested evidence, what cannot be undone; explicit acceptance if untested>
Point of no return: <step after which rollback is impossible — or "none">
Abort criteria: <observable numeric conditions and durations that stop or reverse the action>
Post-action checks: <immediate and delayed checks with observation window, command/artifact, expected exit/count>
Approval: <pending: required approver, scope, window/expiry — or granted: who, scope, window/expiry, pre-authorized ramp/abort/rollback, and any explicitly accepted residual risk>
Verifier: <fresh-context verifier, isolation (harness-enforced | prompt-scoped | human), checks run — or waived (unavailable: reason; by who, scope, window/expiry, accepted risk; executed checks verified, unexecuted behavioral claims inferred)>
```

Rules:

- **Approval covers this action, target, and window only.** A material change to any of them voids it; resubmit the packet. Pre-authorize named ramp steps, observation windows, and abort/rollback steps, or treat each expansion as a new packet.
- **Test the rollback and the state cleanup.** Name and exercise recovery of code, counters, caches, queues, rows, messages, and files, or explicitly accept them as untested. If restore or compensation was not exercised, record it as residual risk; an untested rollback is a hope.
- **No gate theater.** A canary, dry-run, or staging deploy is execution, not approval. The gate is an explicit human approval of the packet *before* crossing the boundary.
- **Execute only what the packet describes.** If execution diverges, stop and re-gate instead of improvising.
- **Post-action verify immediately and through the observation window.** Run the listed checks, compare against the pre-state, inspect logs and the actual diff, and report the post-action state with command/artifact and observed exit/count. A successful command is not a successful outcome; a limiter window or trend needs delayed checks.
- **A failed or ambiguous post-action check is a stop signal.** Execute the pre-authorized rollback or escalate; do not continue to the next step and report success.

## Gate enforcement

A gate in skill text is a soft prompt rule; operator setup for sandboxes, allowlists, and hooks lives in the repository `README.md` (agents must **never** edit their own permission, hook, or sandbox settings). Never rely on a hook or deny-list — or report `harness-enforced` — until smoke-tested in a throwaway sandbox that a forbidden sentinel command is actually blocked (CLI hooks can fail to fire even with `failClosed: true`, and user-level hooks may not reach cloud runners).

## T2 report and sign-off

Every T2 report includes the risk ledger above the report and writes **all** fields below explicitly (use `n/a (pre-gate)` / `n/a (pre-gate local work only)` before crossing the gate boundary):

```text
Tier: <T2 — trigger(s); note pre-gate status, any verifier waiver, accepted risk, or blocked gate>
Outcome: <what changed, or the verdict on the plan/claim>
Changed: <files, systems, or decisions touched — or "none (verification only)">
Interpretation: <none — T2 stops instead of guessing on outcome-changing ambiguity>
Verified: <claim + independent oracle (or "against stated contract") — command/source, provenance (branch@commit + dirty/cwd/env/exit or source/version/date/jurisdiction/locator); redacted>
Inferred: <claim — verified premises, reversal condition, and if high-severity: open risk, named blocker, next check (if one exists), and owner — or "none">
Unverified: <assumption or claim — named blocker/why no evidence, exact next check (if one exists), and owner if blocked — or "none">
Residual risk: <what could still be wrong, and how to check it>
Post-action state: <after execution: command/artifact, exit/count, health, diff — or "n/a (pre-gate)">
Verifier: <fresh-context verifier, isolation (harness-enforced | prompt-scoped | human), checks run — or waived (unavailable: reason; by who, scope, window/expiry, accepted risk; executed checks verified, unexecuted behavioral claims inferred)>
Rollback/compensation: <steps, state cleanup, tested?, what is irreversible — or "n/a (pre-gate local work only)">
Stop reason: <why checking stopped under the stopping rule>
Blocked: <access | environment | authority | approval | T2 gate | missing authoritative oracle | no observable check exists | decision awaited — or "none">
```

**Sign-off-only T2.** When reviewing someone else's proposed action rather than performing it, audit it against the gate-packet fields (blast radius, pre-state and backup, rollback evidence, point of no return, abort criteria, post-action checks). The report (with ledger) is the gate input:

- Mark `Changed`, `Interpretation`, and `Post-action state` as `n/a (sign-off; no execution)`.
- Write `Rollback/compensation` as `executor's rollback: tested/untested — evidence`.
- Append:

```text
Recommendation: <approve | approve-with-conditions | block>
Conditions: <what must hold before the action — or "none">
Decision owner: <who must approve, and by when>
Post-action verification owner: <who checks the result after execution>
```

The sign-off reviewer must not have authored the action or plan; if they did, declare the conflict and do not call the review independent. Do not approve or sign on the user's behalf, and do not execute the action.
